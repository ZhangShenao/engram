# 11. 失败时长什么样

按出现的次序查。多数第一次失败发生在数据或内存，不是学习率的小数点。

## 进程被系统杀掉

统一内存被进程占满时，macOS 会发 `SIGKILL`，终端里有时只剩 `Killed: 9`。训练进程死在反向之前或之中，多半是激活值而不是 LoRA 参数：序列长度、层数和 batch 把 `序列 × 5120 × 层数` 堆过了剩余内存。交换分区会把同一份计算拖进磁盘，速度不再能和冒烟时的每秒 token 比。看活动监视器的内存压力。处理顺序：

1. 退出浏览器和其他占用数 GB 的应用。
2. 确认 `batch_size` 是 1，`grad_checkpoint` 是 true，`max_seq_length` 是 2048。
3. 把 `num_layers` 从 16 降到 8。
4. 用分词器量数据，删掉超过 2048 token 的行。

不要用交换分区硬扛。一旦开始换页，这一轮的速度会掉到没有参考价值。

## 损失从第一步就是 NaN，或者来回跳几个数量级

损失是 `-log(p)`。`p` 在数值上变成 0 时，对数走到负无穷，再往前传到 Softmax 的指数，就会变成 NaN。常见原因是学习率太大，一步把 logit 推到极端，下一步的指数溢出。空的 assistant 内容会让这一段没有可计算的 token，或者让分母出问题。先把学习率改成 `1e-5`，也就是 mlx-lm 示例用的值。rank 和 scale 先保持 8 和 20。数据里如果有空的 assistant 内容，先删掉。

## 训练损失很快接近 0，验证损失变高

这是第 0 章的过拟合，不是优化失败。可训练参数只有几百万，但样本如果只有几十条，这几百万个方向足够把那几十句的 token 概率推到接近 1。训练集损失接近 0，验证集上的下一词并没有更可预测。停掉。正式数据不到几百条时，不要跑十个 epoch。换一批没见过的验证对白，确认损失的分母不是同一批句子。

## 回复格式对了，一问是不是 AI 就出戏

格式 token（星号、换行）在普通对白里出现得多，梯度已经把它们推高。出戏那一句的概率主要来自偏好阶段写进基座的方向，而基座是冻结的。LoRA 只有在同类诱导的样本上反复看到「角色式挡回」时，才会在那条条件上把助手回复的概率压下去。样本太少，平均梯度里没有这个方向。把 system 再写长，只改变推理条件，不增加这条梯度。增加第 7 章的第二类样本。线上提示已经有 re-anchor。

## 回复很会演，记忆块里的名字被忽略或被改写

第三类样本不够，或者 LoRA 只推了语气。在评分表的事实项回升之前，不要加更多纯表演对白。也核对训练 system 里的记忆标题是不是 `[What you remember about the user and story]`，和 `format_memories_block` 一致。

## 线上和 `mlx_lm.generate` 判若两人

先排除两件原理上就会造成差异的事。第一，输入分布不同：`mlx_lm.generate --prompt` 不一定套用训练时的聊天模板，system 里的边界句和 re-anchor 可能根本不在上下文里。把两处的完整 token 前文对齐再比。第二，采样不同：mlx-lm 服务的默认温度在说明里是 0.0，也就是接近贪心。Engram 的聊天补全会带上 `temperature: 0.8`，提取补全带 `0.2`。本地服务器如果忽略这个字段、仍用 0，回复会更呆、更重复。这不是权重退步。curl 时显式带上温度，确认服务器认这个字段，再和检查器里的线上回复比。

## 记忆面板不再增长

第 10 章的环境变量让提取也打到了角色模型上。提取代码在 HTTP 错误或 JSON 对不上时返回空列表。看 Memory 服务的日志，或者暂时去掉 Memory 进程上的密钥，确认确定性提取器恢复之后再评角色。

3. 本地服务器温度默认是 0 时，和线上回复对比会偏哪一边？
